# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

This is a Poetry project using a `src/` layout: the importable package is `dailies` (`src/dailies/`), while the distribution/project name in `pyproject.toml` is still `stfcdailybot` — they intentionally differ, so `[tool.poetry] packages = [{include = "dailies", from = "src"}]` is required for poetry-core to find it (it can no longer auto-detect from the project name). Python and Poetry are both managed via asdf, pinned in `.tool-versions` (`python 3.14.7`, `poetry 2.4.1`) — `asdf install` fetches both if missing, after which plain `python`/`poetry` commands resolve correctly with no env var needed.

- Install dependencies: `poetry install`
- Run the test suite: `poetry run pytest -q`
- Run a single test: `poetry run pytest tests/test_collection.py::test_fetch_then_by_category_filters_daily_events`
- Run the test suite with coverage: `poetry run coverage run -m pytest -q && poetry run coverage report`
- Add a dependency: `poetry add <package>` (or `poetry add --group dev <package>` for dev-only tools)
- Run a script/REPL inside the environment: `poetry run python3 ...`
- Lint: `poetry run ruff check .` (add `--fix` to auto-fix)
- Format: `poetry run ruff format .` (add `--check` to verify without writing)
- Secrets scan: `poetry run detect-secrets scan --baseline .secrets.baseline` (rewrites the baseline with any newly found/removed potential secrets — review the diff before committing); `poetry run detect-secrets audit .secrets.baseline` to triage findings interactively
- Security scan: `poetry run bandit -r src`
- Pre-commit hooks (`.pre-commit-config.yaml`: `ruff-check --fix`, `ruff-format`, `detect-secrets`, `yamllint`, `bandit`, `json-tool`, `tool-versions-match-poetry`): `poetry run pre-commit install` once per clone to wire them into `.git/hooks/pre-commit`; `poetry run pre-commit run --all-files` to run them on demand without committing (note: `--all-files` only covers files git already tracks — pass `--files <path>...` to check untracked new files). Hook revs (`v0.16.5` ruff, `v1.5.0` detect-secrets, `v1.38.0` yamllint, `1.9.4` bandit) are pinned to match the poetry-installed versions — bump both together when upgrading either dependency. `bandit`'s hook is scoped via `files: ^src/` rather than the hook's default `types: [python]` (every `.py` file), since bandit's `B101 assert_used` check would otherwise flag every `assert` in `tests/` — those are idiomatic pytest, not the production code bandit is meant to guard, so only `src/dailies` is scanned. `json-tool` is a local hook (`scripts/check_json.py`) rather than a hosted repo, since `python -m json.tool` only takes one file per invocation and pre-commit hands hooks a batch of filenames at once — the script loops and calls the equivalent of `json.dumps(obj, indent=4, ensure_ascii=True) + "\n"` per file (byte-for-byte what `json.tool`'s CLI produces), auto-rewriting any file that doesn't already match and failing the run so it gets re-staged (same pattern as `ruff-format`). It's scoped via `files: \.json$|^\.secrets\.baseline$` rather than `types: [json]`, because `.secrets.baseline` has no `.json` extension and pre-commit's `identify` library doesn't content-sniff it as JSON. `.yamllint` extends yamllint's `default` ruleset with `document-start: disable` (not requiring a leading `---` on single-document config/workflow files); GitHub Actions' `on:` trigger key is quoted (`"on":`) in `.github/workflows/pre-commit.yml` since YAML 1.1 would otherwise parse the bare word as the boolean `true` (yamllint's `truthy` rule catches this). It triggers on `pull_request` only, not `push` — this repo's actual workflow is a single long-lived branch with a PR kept open against `main` the whole time (`main` itself has never received a direct push past its initial commit), so a bare `push` trigger was firing a second, fully redundant run for every commit already covered by `pull_request`'s `synchronize` event; `push` was dropped once that redundancy was confirmed via `git log --all`, rather than assumed. The hosted hooks (ruff-pre-commit, detect-secrets, yamllint) run in their own isolated environments regardless of the poetry venv, but `.github/workflows/pre-commit.yml` still installs poetry and runs `poetry install` (dev dependency group included) before invoking `pre-commit/action`, since local hooks like `json-tool` run via `language: system` — they use whatever `python3`/packages are already on `PATH` rather than a pre-commit-managed venv, so CI needs the project's dependencies actually installed for those to have what they need (`json-tool` itself is stdlib-only today, but this keeps CI correct for any future local hook that isn't). The job runs inside a bare `debian:bookworm-slim` container rather than the runner's default toolchain, since neither Python nor Poetry come from the image — both are installed by `asdf-vm/actions/install@v4.0.1`, which reads `.tool-versions` and installs the exact `python 3.14.7`/`poetry 2.4.1` pins it lists, mirroring the local `asdf install` flow described in the intro above instead of getting Python from a pinned base image and Poetry from `pip`. `v4.0.1` specifically (not `v3`, which this workflow briefly used) — `v3` predates asdf's Go rewrite (0.16+); it `git clone --branch master`s the `asdf-vm/asdf` repo, which no longer contains a runnable shell script at that path, so every job using it failed with `Unable to locate executable file: asdf`. `v4.0.0`'s changelog is literally "support asdf >= v0.16.0": it downloads the correct platform release tarball instead of cloning the repo. Even on `v4.0.1`, though, the action's `install` step always ends by shelling out to a bare `asdf install` (confirmed by reading its bundled `main.js` — the `skip_install` input only gates whether the `asdf` CLI itself gets installed, not the tool-versions install step, so there's no input to skip it), and bare `asdf install` processes `.tool-versions`' plugins alphabetically, meaning it tries `poetry` before `python`. The `poetry` plugin's install script shells out to `python3` to bootstrap itself, and with no Python installed yet it either failed outright (this container, no system `python3` at all) or silently bootstrapped Poetry against the wrong interpreter (the plain `ubuntu-latest` runner briefly used for `tests.yml` had a system Python fallback) — the latter then made the later `poetry install --no-interaction` step try to write into that system Python's non-writable site-packages and fail with a `PermissionError`. The fix uses the action's `before_install` input ("Bash script to run after plugins are installed but before `asdf install`"): it runs `asdf install python` (no explicit version — like the action's own later bare `asdf install`, this reads `.tool-versions` itself) and `asdf reshim python` first, so by the time the action's own bare `asdf install` runs, python's shim already exists and poetry's install script finds a working `python3` on `PATH`. A second, separate shim gap showed up after that fix: `asdf reshim` only wires up shims for executables that existed the last time it ran, so the `pre-commit`/`ruff`/`bandit`/etc. console scripts that `poetry install` newly writes into the asdf-installed Python's `bin/` aren't reachable as bare commands until reshimmed again — `pre-commit/action@v3.0.1` invokes plain `pre-commit` (not `poetry run pre-commit`), so it failed with `pre-commit: command not found` until a `Reshim newly installed console scripts` step (`asdf reshim python`) was added right after the shared setup, in `pre-commit.yml` only — `tests.yml` only ever runs things via `poetry run`, so it doesn't need this. Everything from that shared setup onward — installing `curl` and the CPython build toolchain, marking the workspace as a safe git directory, the `asdf-vm/actions/install` + `before_install` block, and `poetry config virtualenvs.create false && poetry install` — lives once, in `.github/actions/setup-python-poetry/action.yml`, a local composite action both workflows call via `uses: ./.github/actions/setup-python-poetry`; it used to be copy-pasted into both workflow files and had already silently diverged (the reshim step existed in one file but not the other) before being factored out. Only `apt-get install git ca-certificates` (as its own tiny step, named "Install git and CA certificates") stays duplicated ahead of `actions/checkout@v4` in each workflow, since a local composite action can't be `uses:`'d before the repo containing its `action.yml` has been checked out — and `ca-certificates` has to be installed at that same point too, not deferred into the composite, because `actions/checkout`'s own HTTPS git clone needs it to verify TLS (checkout failed with "server certificate verification failed" the one time this was tried). Because the asdf `python` plugin builds CPython from source (via `python-build`) rather than fetching a prebuilt binary, the composite action's first step `apt-get install`s the standard CPython build dependencies (`build-essential`, `libssl-dev`, `zlib1g-dev`, `libbz2-dev`, `libreadline-dev`, `libsqlite3-dev`, `libncursesw5-dev`, `xz-utils`, `tk-dev`, `libxml2-dev`, `libxmlsec1-dev`, `libffi-dev`, `liblzma-dev`) alongside `curl`/`ca-certificates` (for downloading the `asdf` release tarball and python-build's own downloads). `poetry config virtualenvs.create false` is set first so packages install into the asdf-installed Python's site-packages directly (no separate venv), making them importable by plain `python3` calls (as `json-tool`'s `entry:` does) without needing a `poetry run` wrapper. Editing tracked files (including markdown docs) can trip `detect-secrets`' `KeywordDetector` on innocuous phrases like "Secrets scan:" — if `pre-commit run --all-files` reports a new finding, re-run `detect-secrets scan --baseline .secrets.baseline` to fold it into the baseline (and `detect-secrets audit .secrets.baseline` to mark it `is_secret: false` if it's a false positive) before committing, or CI will fail on the stale baseline.

`tool-versions-match-poetry` (`scripts/check_tool_versions.py`) keeps `.tool-versions` honest against the poetry config it's meant to mirror: it checks `.tool-versions`' `python` pin satisfies `pyproject.toml`'s `[project] requires-python` range (a lightweight hand-rolled specifier parser — no `packaging` dependency needed for the simple `>=X,<Y` form used here), and checks `.tool-versions`' `poetry` pin exactly matches the "generated by Poetry X.Y.Z" version recorded in `poetry.lock`'s header comment (the closest thing to an authoritative "which poetry CLI produced this lock" record, since poetry.lock/pyproject.toml don't otherwise pin the CLI version — only `poetry-core`, the build backend, is versioned in `[build-system]`). Bump `.tool-versions` whenever `requires-python` changes or `poetry lock` is run with a different poetry version.

`.github/dependabot.yml` enables Dependabot version-update PRs for the `pip` ecosystem (which covers Poetry's `pyproject.toml`/`poetry.lock`, per GitHub's docs) and the `github-actions` ecosystem (keeps the `uses:` action pins in `.github/workflows/*.yml` current), both on a `weekly` schedule against the repo's default branch (`main`, left implicit rather than set via `target-branch` — Dependabot always diffs against the default branch unless overridden). This isn't a GHA workflow with its own `on:` triggers — Dependabot runs on GitHub's own schedule and opens PRs itself, rather than reacting to `push`/`pull_request` events — so there's no `push`/`pull_request`-to-non-`main` trigger to configure here; those PRs land as ordinary branches/PRs and get exercised by the existing `pull_request`-triggered `pre-commit.yml` and `tests.yml` workflows like any other PR. It does not cover pre-commit's own hosted-hook revs (`ruff-pre-commit`, `detect-secrets`, `yamllint`, `bandit`) — GitHub has no Dependabot ecosystem for pre-commit's `.pre-commit-config.yaml`, so those still need bumping by hand. `dependabot.yml`'s `schedule.interval` only governs routine, non-security version-bump PRs — it has no bearing on vulnerability response speed. Security coverage is a separate, repo-level GitHub feature (Settings → Code security → "Dependabot alerts" and "Dependabot security updates"; checked via `gh api repos/<owner>/<repo>/vulnerability-alerts` and `.../automated-security-fixes`), already enabled on this repo, that fires immediately/continuously whenever a CVE is disclosed for something in `poetry.lock`, independent of the `weekly` interval above — there's nothing to configure for it in this file.

`.github/workflows/tests.yml` runs the test suite with coverage on `pull_request` (opened/synchronize/reopened by default, so it re-runs on every push to a branch with an open PR) and posts the result as a PR comment via `py-cov-action/python-coverage-comment-action@v4.3`. It's a separate workflow from `pre-commit.yml` rather than an extra job there, since it needs its own `pull_request`-only trigger and a `pull-requests: write` permission the lint job doesn't need. It runs in the same `debian:bookworm-slim` container and calls the same `.github/actions/setup-python-poetry` composite action (see `pre-commit.yml`'s entry above for what that does and why) as the pre-commit job, so both workflows build Python/Poetry from the identical, `.tool-versions`-pinned environment rather than one of them drifting onto whatever `ubuntu-latest` happens to ship, or the two copies of the setup silently diverging. Coverage is collected via `coverage run -m pytest -q` (not `pytest --cov`) because the action reads `coverage.py`'s own `.coverage` data file directly; `[tool.coverage.run]` in `pyproject.toml` sets `source = ["dailies"]` (the installed package name, so `src/`-layout paths resolve) and `relative_files = true`, which the action's docs require so paths recorded during the CI run match up when the action re-reads them. The setup deliberately skips the action's optional companion job that would run on pushes to `main` to persist coverage history/badges to a dedicated data branch — that mode needs a `contents: write` permission and an unprotected storage branch this project doesn't otherwise need; without it, each PR comment shows the run's total coverage rather than a diff against `main`, which was an accepted tradeoff for simplicity. `pull_request` was chosen over triggering on raw `push` events to non-`main` branches because the coverage-comment action's own docs call push-triggered comment posting only partly supported ("you will not have the best user experience") and don't fully document it — `pull_request` still reruns on every push to a branch with an open PR, so it covers the same practical case through the officially supported path.

## Architecture

The package pulls STFC event data from the JSON API at `https://stfc-cfd-api.fly.dev/api/events` — the backend behind the `stfc.cfd` calendar (a client-rendered React app). We talk to the API directly rather than the frontend: `stfc.cfd`'s `robots.txt` explicitly disallows AI crawlers (including `ClaudeBot`) and sets `Content-Signal: ai-train=no`, so scraping its rendered HTML was ruled out; the API host has no such restriction, and the user operating this project confirmed they're authorized to access it directly. `GET /api/events` returns the full flat event list (no pagination observed, ~700+ records) with fields like `eventCategory` (`daily` / `weekly` / `monthly` / `none`), `eventFormat` (`SMS` / `SLB` / `ALB` / etc.), `priority`, ops-level gating, and explicit `startTime`/`endTime` — a much richer, more direct source than the earlier stfc.ovh HTML-table scraper this replaced.

`Event` (`src/dailies/event.py`) is a `pydantic.BaseModel` with `alias_generator=to_camel`, so it validates and maps the API's camelCase JSON directly onto typed, snake_case fields; timestamps parse straight to timezone-aware `datetime`s. Several fields the sample data initially suggested were required turned out to be nullable in the wild (e.g. `description`) — pydantic's validation caught this against the live API, so when adding fields, check nullability against a real response rather than assuming. It's in its own module rather than `client.py`, since it's a data model, not part of talking to the API.

`Client` (`src/dailies/client.py`) is the low-level HTTP layer: it owns `DEFAULT_API_URL`, `DEFAULT_TIMEOUT`, and the private `_EVENTS_PATH`/`_USER_AGENT` constants as class attributes, and `fetch_events(*, timeout=DEFAULT_TIMEOUT) -> list[dict]` as an instance method against `self.base_url` (set via `Client(base_url=DEFAULT_API_URL)`). It doesn't import `Event` at all — nothing in `client.py` returns `list[Event]`, since anything that produces or filters a set of events belongs on `EventCollection` instead (`src/dailies/collection.py`).

`EventCollection` is an in-memory, always-sorted-by-`start_time` container. `EventCollection.fetch(client: Client | None = None)` is the classmethod entry point — it defaults to a plain `Client()` if none is given, calls `client.fetch_events()`, and validates the result via `TypeAdapter(list[Event])` in one step; pass a `Client` configured with a different `base_url`/timeout to point it elsewhere. `at(event_time)`, `by_category(...)`, `by_active(...)`, and `by_priority(...)` each return a new `EventCollection`, so they chain (`EventCollection.fetch().by_category("daily").by_priority("arc")`); the containment check in `at()` is start-inclusive/end-exclusive, matching how the API's back-to-back events abut. `start_times`/`end_times` expose the sorted, de-duplicated set of boundary timestamps in the collection — useful for enumerating the moments where the active set changes without guessing at fixed reset hours (unlike stfc.ovh, this API's events don't all land on a fixed daily reset clock).

Tests: `tests/test_client.py` only covers `Client().fetch_events()` (raw JSON, no `Event`/`EventCollection` involved). Everything that touches `Event` parsing or filtering lives in `tests/test_collection.py`, either against synthetic in-memory `Event`s or via `EventCollection.fetch()` mocked with `responses` against the shared fixture `tests/fixtures/events_sample.json` (nullable-field and `repeatConfig` edge cases from real API responses), asserting against `Client.DEFAULT_API_URL`.
